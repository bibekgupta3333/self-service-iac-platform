# Changelog

All notable changes to this project are documented here.
Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). The project uses [Semantic Versioning](https://semver.org/).
Infrastructure modules are versioned separately with tags `modules/<name>/vX.Y.Z`. Their changes go in each module's own `CHANGELOG.md`.

## [Unreleased]

### Changed
- Portfolio docs (WBS 10.4, write-up part): `README.md` rewritten as a front page (what works today, quickstart, layout, status and limits), and a new `docs/case-study.md` covering the problem, design decisions, review hardening, testing and trade-offs.
- Terratest module dependencies: `golang.org/x/crypto` 0.52.0, `github.com/klauspost/compress` 1.18.7 and `github.com/ulikunitz/xz` 0.5.14 (replaces the Dependabot PRs #5, #6 and #7).
- Drift follow-ups: the kept `Error:` line of a failed check is cut after the resource identifier, so provider text that echoes a value cannot survive (the scan's own fixed messages are an explicit allow-list and pass unchanged); suppression of an ignored finding compares against the newest report that is not a failed check; suppressed copies are audited with `suppressed: true`; `drift scan --error-file` reads at most 1 MB of bytes. S3 refresh noise: `lifecycle { ignore_changes }` on `aws_s3_bucket` was tried against LocalStack and does not change a refresh-only plan, so `modules/s3` is unchanged and docs/06 lists the options.
- Review follow-ups: the route policy middleware is mounted unconditionally and the API refuses to start without a policy table (`Deps.Validate`); event streams end when the session user's platform admin flag changes (`StreamSession.Alive` now also returns it); update, destroy and create role checks use the principal's platform admin flag through `identity.Principal.EffectiveRole`, so the dev-mode user can update and destroy the stacks it sees without being a database admin.

### Added
- Recovery (WBS 8.7):
  - `internal/recovery.Classify`: a pure classifier of failed pipeline stages into `transient` (throttling, provider 5xx, timeouts, state-lock contention, eventual consistency, lost runner), `config` (policy deny, plan mismatch, validation, plan error) and `infra` (partial apply, quota, permissions, smoke), table-tested with real Terraform and AWS error strings; unknown failures are never transient.
  - Automatic retries: a `requests.RetryPolicy` hook (`ApplyDriver.WithRetry`) lets recovery decide, in the apply report's transaction, before a failed run fails the request; a transient failure keeps the request `applying`, fires `apply_retry` within the state machine's cap (2), audited, and enqueues `recovery.apply_retry` after 2 min, then 10 min. A retry that cannot run fails the request (`retry_not_run`). The dispatcher takes a free stack lock back for the request and re-dispatches `apply.yml` with the request's ids and approved plan hash, exactly once (claimed before GitHub is called; a failed dispatch is recorded and never re-sent). Migration `0016_apply_failures`.
  - `apply.yml` reports a redacted excerpt of `apply.log` (`report --error-log`, `iacp-report` input `error-log`): Terraform's `Error:` lines cut after the resource identifier, at most 500 characters, with a fixed fallback, and `error.signals` taken only from a fixed vocabulary of AWS error codes and Terraform phrases that the classifier's rules are built from (shared Go/Python test vectors). The rules live in shared helpers (`internal/tferror`, `tools/stack_pipeline/tf_error.py`) that drift's summary now uses too (the `Authorization: Bearer` form is redacted as well), and the API redacts reported error messages again before storing them (`runs.RedactError`). A retry that cannot run leaves the stack to a waiting request that already holds the lock.
  - `POST /v1/stacks/{id}/rollback` (maintainer+, route policy and team role): an update request restoring the stack's last applied configuration through the normal request path, refused for destroyed or busy stacks and when nothing can be restored; the spec and audit record `rollback_of`, and the PR is titled, labelled (`iacp:rollback`) and explained as a rollback. `requests.Service.Replay` answers a retried call with the request it created.
  - Break-glass `state-surgery.yml`: `workflow_dispatch` from main, approval in the `break-glass` Environment, allow-listed operations (`state rm`, `state mv`, `import`, `force-unlock`) with strictly validated arguments, dry run by default, LocalStack under ADR-0009, inputs only via env and never echoed raw, Terraform output inside `::stop-commands::`. `tools.stack_pipeline state-surgery validate|run|report`, and `POST /v1/internal/state-surgery` (route class `state_surgery`, OIDC only) appending one `state.surgery` audit event per run attempt, naming the verified `actor` claim, `approved_via` only for runs from the `break-glass` job (`environment` claim), and recording refused runs without a known stack on the run itself. A rollback to a yanked module version is refused with `422 rollback_target_yanked`.

Positive and negative tests (coverage stays above 90), fixtures and `verify.sh` cases.

- Apply reports drive request and stack status (WBS 5.3 backend half), closing the loop so update and destroy requests work end to end:
  - `POST /v1/runs` with `pipeline: apply` moves the request `approved → applying` on the first accepted report and `applying → applied` or `failed` when the run finishes, using `Request.Fire` through the pure `requests.DecideApply`; replays and out-of-order reports are idempotent, and a late report for a terminal request is stored and ignored (`request.run_report_ignored`). `validate` reports are stored only: a passed validation is never an approval.
  - The stack follows through `StackStatusWhileApplying` / `StackStatusAfterApply` (`provisioning`, `updating`, `destroying`, then `active`, `destroyed` with `destroyed_at`, or `failed`) and records the applied outputs, `last_applied_sha` and `last_applied_request_id`; each move is audited as `stack.status_changed` (`stack.destroyed` too) next to the request's `request.transitioned`.
  - A failed `smoke` stage no longer fails the run: when the apply stage passed and the smoke test is the only failure (`apply.yml` sends `summary` from `job.status`, which the smoke step turns red), the run is `succeeded`, the request `applied`, the stack `active` with the new `stacks.health = degraded` (migration `0011`). A failed `release` after the verdict is stored in the run, audited as `request.lock_release_failed` with the lock's current state, and never flips an applied request.
  - The terminal transition releases the stack lock and promotes the next waiter in the same transaction through the existing `commit` path (its publish job is scheduled). The report transaction now locks the `stacks` row `FOR UPDATE` first, so concurrent reports of one stack serialise.
  - `DELETE /v1/internal/stacks/{id}/lock` is idempotent for a terminal request that presents its own token (`already_released: true`), so the `release` step of `apply.yml` stays green after the API has released the lease.
  - Hardening: the released token is accepted only for a run already recorded for that request (a new run id or attempt is `409`), late reports are not merged into a finished run's stages, `Release` decides the idempotent no-op before any write, the purge function clamps its cutoff to at least one hour in SQL, and `Deps.Validate` also requires `Roles`.
  - A report for a terminal request that carries the request's own (already released) token is accepted and ignored; any other stale token is still `409`. Fencing token, `head_sha`, workflow and event allow-lists and run/attempt equality are unchanged and covered by tests that show a rejected report moves nothing and records nothing. A request that was never approved gets `409 request_not_applying`.
  - `GET /v1/stacks` and `/{id}` show `health` and the `lock` holding the stack (no fencing token); apply outputs must be a JSON object.
  - Tests: pure `DecideApply`, `Progress`, `SmokeExplainsFailure` and `SettleRunStatus` tables, service-level `ApplyIn` tests, and Postgres integration tests for the full create, update, destroy, failed-plan, smoke-degraded, cancelled and release-failed loops, plus the existing report/release deadlock test with applying requests. Verified locally against the API with the shared token: create, update (smoke failed), destroy, then `stack_destroyed` for further update and destroy.
- Trusted proxies: `IACP_TRUSTED_PROXIES` (CIDRs or addresses, default none). Only when the immediate peer is trusted is `X-Forwarded-For` read, from the right, taking the first untrusted entry; it keys the login rate limiter and is the audit `actor_ip` (login and `rbac.denied` events). Without it the limiter is one global bucket behind the portal proxy. The portal proxy must still forward the client address in `X-Forwarded-For` and allow the header (documented in `backend/README.md`, left for a later portal change).

### Security
- The backend fails closed: it binds to loopback by default, refuses to start without `IACP_AUTH_MODE`, keeps internal endpoints behind a constant-time token check, and enforces team membership on request creation.
- The API runs as the `iacp_app` role, which can only INSERT and SELECT on `audit_events`. Triggers block UPDATE, DELETE and TRUNCATE.
- The local stack binds LocalStack and Postgres to loopback only. Images are pinned by digest.
- `make` forces LocalStack dummy credentials and unexports `AWS_PROFILE` and session tokens.
- Machine endpoints fail closed: with neither OIDC nor `IACP_INTERNAL_TOKEN` configured they reject every call, a half OIDC configuration stops the API from starting, and a genuine token from a workflow outside the allow-list gets `403 workflow_not_allowed`.
- OIDC callers are scoped per route class: lock routes accept only `apply.yml`/`ttl-reaper.yml` on main, catalog indexing only `module-release.yml` on main, so a pull-request token only reaches `/v1/runs`. Each pipeline also has an `event_name` allow-list (`pull_request_target` and `workflow_run` never qualify), and run reports must carry the token's `sha`.
- The JWKS endpoint must be https (loopback excepted) and redirects are not followed. Fetches are shared (singleflight) and detached from the caller, so a disconnecting client cannot block key refreshes.
- When `IACP_OIDC_REPOSITORY_ID` is set every token must carry it; the API warns when it is unset.
- `iacp_app` can only SELECT, INSERT and UPDATE `pipeline_runs`.
- `/metrics` shares the API listener but is closed by default. It answers direct loopback peers, never a request with forwarding headers, and otherwise needs `IACP_METRICS_TOKEN`, which is separate from the internal token. Methods outside the standard set are labelled `OTHER`, so junk methods cannot add series. The loopback rule assumes no same-host proxy relays outside traffic without forwarding headers.
- A replayed GitHub OIDC token or one without `jti` gets a 401. A replay-store outage also refuses the token, but with a retryable `503 replay_store_unavailable` and its own log line. A claim deletes only its own expired row; a background sweep purges the rest in batches of 1,000. `iacp_app` has no UPDATE on `oidc_jti`.
- Pull-request tokens can now also read the budget context, which is read-only, for any team's stack path (an accepted exposure, documented in docs/07). They still cannot take locks or index the catalog.
- `tools/stack_pipeline` mints a new GitHub OIDC token for every API request, retries included, because the API now rejects a reused `jti`; the shared internal token is still reused.
- `tools/codeowners` only counts git-tracked stack roots and rejects `platform_paths` under `/environments/<env>/`, which team rules would shadow.
- `security-events: write` is granted only to the `code-scanning` upload jobs, which run no PR code; fork and Dependabot PRs skip the upload. Stack SARIF paths always stay inside the repository, and a run's own `automationDetails` is dropped so a PR cannot pick its category. `INFRACOST_API_KEY` is passed only to the `cost` job, which runs no PR code.

A connection now counts as failed only if it closed within 10 seconds without an event (a heartbeat alone does not count, so a proxy that sends one and closes ends in the polling fallback) or went silent with nothing received;
  - an idle watchdog cuts a connection after 45 seconds without any bytes and resumes with `Last-Event-ID`;
  - after a healthy connection, reconnects start at least 3 seconds apart, so a stream that sends one event per connection cannot loop tightly;
  - the SSE parser scans each chunk once instead of re-parsing the whole buffer (which was quadratic), caps a frame at 256 KiB, and drops an oversized frame and resynchronises;
  - a `200` that is not an event stream has its body cancelled;
  - the polling fallback (`RequestPoller`) stops on 401, 403 and 404 with a message and pauses while the tab is hidden;
  - a request that was already terminal when the page loaded opens no stream;
  - pull request links are rendered only for `https://github.com/` URLs;
  - the destroy dialog clears the typed name and justification on Cancel and Escape, ignores a second submit while one is in flight, and stays open on Escape while it is;
  - without a spec-carrying request, the update page says plainly that the stack's real resources are unknown;
  - new tests for the role mirror with an unknown environment and for a resumed stream that replays a seq. The stream and resume behaviour is documented in docs/06 §8.1.
- The post-apply smoke test no longer fails stacks with CloudWatch alarms on LocalStack, which drops the tags passed to `PutMetricAlarm`: `aws_cloudwatch_metric_alarm` is left out of the tag checks (`EMULATOR_UNTAGGED`) and named in the report. For the same reason the pr-validate apply round trip checks the re-plan with `tools.stack_pipeline converged` instead of `-detailed-exitcode`: it still fails on any leftover change except a tag-only update of an alarm.
- Portal request form: focus moved to the error summary in a microtask that could run before the first error's summary existed, so the first failed submit left focus on the button. It now moves in an effect.
- The catalog index accepted the category `data`, which `module.yaml` cannot carry, and rejected `database` and `cache`, which it can. It now accepts exactly the categories in `modules/_shared/module.schema.json`, so the `dynamodb` manifest indexes.
